## Spectre 0.55 migration shape

```diff
-public override async Task<int> ExecuteAsync(CommandContext context, TSettings settings)
+protected override async Task<int> ExecuteAsync(
+    CommandContext context,
+    TSettings settings,
+    CancellationToken cancellationToken)
 {
-    using var cts = new CancellationTokenSource(TimeSpan.FromSeconds(30));
+    using var cts = CancellationTokenSource.CreateLinkedTokenSource(cancellationToken);
+    cts.CancelAfter(TimeSpan.FromSeconds(30));
     ...
 }
```

`protected override` is required (CS0507 if `public`); CT must be the
last parameter (CA1068). The internal-timeout token now combines with
the framework's Ctrl-C token, so a user pressing Ctrl-C interrupts the
command immediately rather than waiting up to N seconds for the timeout
to fire.

The trim cascade is unchanged from 0.50: same `<NoWarn>` list on the
publish project, same `[DynamicDependency]` rooting in `AotRoots`. ILC
inlines a `throw` for `OpenCli.OpenCliParser.Parse` because Spectre 0.55
references `NJsonSchema` for a JSON-Schema feature we never invoke; the
runtime never reaches the throw site.

## `.vmem` heuristic refinement — root cause

Direct filesystem inspection of the build host's `vault-3` VM directory
after the v0.2.0 round-trip (where post-suspend status incorrectly
reported `stopped`):

```text
H:\VMS\NexusPlatform\01-foundation\vault-3\
  vault-3.vmx
  vault-3-3c85c1f6.vmem        2 GB    <-- session-suffixed memory paging file
  vault-3-3c85c1f6.vmem.lck/
  vault-3.vmsd                 0
  vault-3.nvram                8.4 KB
  disk-cl1.vmdk                2.7 GB
  ...
```

VMware Workstation Pro 17.5+ encodes a session UUID into the memory
paging filename: `<vm-name>-<8hex>.vmem`. The v0.2.0 heuristic was:

```csharp
public static string GetVmssSidecar(string vmxPath) => Path.ChangeExtension(vmxPath, ".vmss");
public static string GetVmemSidecar(string vmxPath) => Path.ChangeExtension(vmxPath, ".vmem");
// classifier: File.Exists(GetVmssSidecar(vmx)) || File.Exists(GetVmemSidecar(vmx))
```

`Path.ChangeExtension(vmx, ".vmem")` produces `vault-3.vmem` (no UUID),
which never exists on Workstation Pro 17.5+. The heuristic was always
returning `false`, so the classifier defaulted suspended VMs to
`Stopped`.

Fix: directory-prefix search.

```csharp
public static bool HasSuspendedStateSidecar(string vmxPath)
{
    var dir = Path.GetDirectoryName(vmxPath);
    var baseName = Path.GetFileNameWithoutExtension(vmxPath);
    return Directory.EnumerateFiles(dir, $"{baseName}*.vmem").Any()
        || Directory.EnumerateFiles(dir, $"{baseName}*.vmss").Any();
}
```

Per the `vmware_per_vm_folders` canon, every VM lives in its own
subdir, so the search is bounded — never crosses into another VM's
files. Catches both:
- Older Workstation: `vault-3.vmem`
- Workstation Pro 17.5+: `vault-3-3c85c1f6.vmem`

Tests: 5-fixture truth table in
`tests/Nexus.Cli.Tests/Vmware/VmrunArgsTests.cs::HasSuspendedStateSidecar_Detects_Suffixed_And_Unsuffixed_Vmss_Or_Vmem`
plus the `vault-3-3c85c1f6.vmem` shape in
`InfrastructureServiceTests.SuspendAsync_Recognises_Session_Suffixed_Vmem_As_Already_Suspended`.

## Live `suspend → status → resume` round-trip on `foundation/vault-3`

```text
==[STEP 1] PRE-STATE ==
── foundation / vault-3 · 1 VMs ──────────────────────────────────────
| Name    | State   | OS    | VMnet10        | VMX                                            |
| vault-3 | running | deb13 | 192.168.10.123 | H:\VMS\NexusPlatform\01-foundation\vault-3\vault-3.vmx |

==[STEP 2] SUSPEND ==
── suspend · foundation · 1 VMs ──────────────────────────────────────
  ✓ vault-3                suspended

==[STEP 3] POST-SUSPEND STATUS (expect: suspended, not stopped) ==
── foundation / vault-3 · 1 VMs ──────────────────────────────────────
| Name    | State     | OS    | VMnet10        | VMX                                            |
| vault-3 | suspended | deb13 | 192.168.10.123 | H:\VMS\NexusPlatform\01-foundation\vault-3\vault-3.vmx |

==[STEP 4] RESUME ==
── resume · foundation · 1 VMs ───────────────────────────────────────
  ✓ vault-3                resumed

==[STEP 5] POST-RESUME STATUS ==
── foundation / vault-3 · 1 VMs ──────────────────────────────────────
| Name    | State   | OS    | VMnet10        | VMX                                            |
| vault-3 | running | deb13 | 192.168.10.123 | H:\VMS\NexusPlatform\01-foundation\vault-3\vault-3.vmx |
```

**Step 3 is the key one** — `state = suspended`, not `stopped`. v0.2.0's
behaviour on the same input was `stopped`. The fix works.

Vault Raft retained quorum on `vault-1` + `vault-2` during the suspend
window; `vault-3` returned to a running state at the end of the
round-trip; no orphaned `.lck` files; clean cycle.
