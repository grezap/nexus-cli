## Pre-flight: Vault HA recovery

A build-host reboot prior to the smoke triggered a known cascade
documented in `feedback_vault_transit_boot_race_recovery.md` (memory):

  - `vault-transit` came up SEALED (Shamir-only — no auto-unseal below it).
  - `vault-1/2/3` failed to fetch their seal keys at boot, exit-1'd, and
    systemd gave up after 3 retries in 5 seconds.
  - HA cluster sat in `failed` state until manual recovery.

Recovery via `nexus-infra-vmware/scripts/recover-vault-ha.ps1`:
  1. Submit Shamir unseal keys to vault-transit (kept in PowerShell
     variables; never echoed to transcript).
  2. SSH each HA node → `sudo systemctl reset-failed vault &&
     sudo systemctl start vault`.
  3. Install a permanent systemd drop-in
     (`/etc/systemd/system/vault.service.d/10-restart-tolerance.conf`)
     bumping `StartLimitBurst=15`, `StartLimitIntervalSec=600`,
     `RestartSec=10`. Future host reboots that race transit will retry
     for ~10 minutes before giving up, giving the operator time to
     unseal transit.

Post-recovery: cluster_name=`nexus-vault`, vault-1 active, vault-2/3
standby. Then ran the failover-test smoke against the (now healthy) Consul.

## SSH key discovery — operator surprise

`SshKeyDiscovery` checks `NEXUS_SSH_KEY` env, then falls through to
`~/.ssh/id_ed25519` and `~/.ssh/id_rsa`. The build host had an `id_ed25519`
file but it's the operator's GitHub key, not the lab-VM key — the
correct key for the lab is `nexus_gateway_ed25519`. SSH.NET (unlike
plain `ssh` via ssh-agent) reads the key file directly, so the
operator must set `NEXUS_SSH_KEY` explicitly for non-default key names:

```pwsh
$env:NEXUS_SSH_KEY = "$env:USERPROFILE\.ssh\nexus_gateway_ed25519"
```

Documented in README + this verification doc. v0.3.x candidate
improvement: also read `~/.ssh/config` to honour `Host`-blocks
`IdentityFile` overrides.
