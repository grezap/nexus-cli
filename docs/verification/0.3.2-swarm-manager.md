## Live smoke — `failover-test swarm-manager --yes` (run 1)

Pre-state cluster-status: 6 Consul alive (leader swarm-manager-2),
3 Nomad servers (leader swarm-manager-3), 3 Nomad clients ready,
Docker Swarm raft leader = swarm-manager-1.

```text
> nexus.exe failover-test swarm-manager --yes
── ● GREEN  recovered  failover-test swarm-manager  (2026-05-13 21:01:40Z) ──
  original leader : swarm-manager-1
  new leader      : swarm-manager-3
  RTO             : 21.59s
  recovery        : recovered

  Timeline (seconds from start)
  ┌───────────────────────┬────────┐
  │ Phase                 │ Offset │
  ├───────────────────────┼────────┤
  │ pre-flight complete   │ 0.36   │
  │ failure injected      │ 1.87   │
  │ new leader observed   │ 23.46  │
  │ recovery attempted    │ 27.80  │
  │ cluster healthy again │ 30.00  │
  └───────────────────────┴────────┘
exit=0
```

What happened in the timeline:
- **0.00→0.36s** — pre-flight: load `vms.yaml`, SSH each manager and
  parse `docker node ls` for the current Leader, pick non-leader
  for polling (`swarm-manager-2`).
- **0.36→1.87s** — `vmrun.exe -T ws suspend "H:\\VMS\\NexusPlatform\\06-orchestration\\swarm-manager-1\\swarm-manager-1.vmx"`
  takes ~1.5s for VMware to save RAM state.
- **1.87→23.46s** — **21.59 seconds of raft re-election.** Docker
  Swarm raft's default `ElectionTick=10` ticks at ~1s each, so the
  heartbeat timeout fires ~10s after the suspended manager misses
  its first heartbeat. Quorum reconvenes on swarm-manager-2 +
  swarm-manager-3, electing swarm-manager-3 as new Leader.
- **23.46→27.80s** — `vmrun.exe -T ws start "...vault-1.vmx" nogui`
  takes ~4s for VMware to restore the saved RAM state.
- **27.80→30.00s** — Docker engine on swarm-manager-1 wakes up, rejoins
  the Swarm cluster as Reachable (not Leader; new Leader retains).
  `docker node ls` now reports all 3 managers `Status=Ready`.

Vault Raft on vault-1/2/3 was COMPLETELY UNAFFECTED — it's a separate
cluster in the foundation tier with no dependency on the swarm-manager
nodes. Consul + Nomad on swarm-manager-1 returned to service when the
VM resumed (their leader roles on swarm-manager-1 had already migrated
to other managers during the suspend window). Running Nomad allocations
on workers were unaffected (the scheduler was briefly leaderless but
no allocations died).

Run 2 picked up the leader rotation from run 1 (Swarm raft had moved
to swarm-manager-3 after run 1 stopped swarm-manager-1) and successfully
suspended swarm-manager-3 + waited for swarm-manager-2 to win the new
election. RTO 21.314s — consistent with Docker Swarm raft's
heartbeat-based election timing (always ~20-25s on this cluster).

The `clusterHealthyAgainSec` of 36.58s here vs 30.00s in run 1 reflects
that VMware took marginally longer to restore the second VM's RAM state.

## RTO comparison across scenarios

| Scenario | Failure mechanism | Observed RTO |
|---|---|---|
| `consul-leader` (v0.3.0) | service-level `systemctl stop consul` | 1.55s, 2.565s |
| `nomad-leader` (v0.3.1) | service-level `systemctl stop nomad` | 3.63s, 2.716s |
| `swarm-manager` (v0.3.2) | **host-level `vmrun suspend`** | **21.59s, 21.314s** |

The order-of-magnitude jump for `swarm-manager` is expected: Docker
Swarm raft's heartbeat-based election requires multiple missed
heartbeats before declaring a peer dead, whereas Consul + Nomad notice
a clean service stop almost immediately (the OS RST's their TCP
connections + raft sees the peer drop with no timeout).
