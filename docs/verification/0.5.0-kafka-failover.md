# v0.5.0 — `kafka failover` verification

> Canon: `nexus-platform-plan/MASTER-PLAN.md` line 258 (Kafka DR east→west < 60 s gate). Design: [`ADR-0008`](../adr/ADR-0008-kafka-failover-demo-grade-via-ssh.md).

This document is the v0.5.0 exit-gate proof: the fifth and last master-plan verb — `nexus kafka failover` — is implemented as a demo-grade DR scenario, both directions exercised against the live Kafka tier (`nexus-infra-kafka` `v0.1.0`), with measured RTOs.

## What shipped

Two subcommands matching the established `failover-test` pattern:

```
nexus kafka failover east-to-west [--json] [--no-color] [--yes]
nexus kafka failover west-to-east [--json] [--no-color] [--yes]
```

Per [`ADR-0008`](../adr/ADR-0008-kafka-failover-demo-grade-via-ssh.md), each subcommand:

1. **Pre-flight** — SSHes to a target-cluster broker and runs `kafka-metadata-quorum.sh ... describe --status`. Refuses to inject failure if the target isn't reporting a `CurrentLeader`.
2. **Inject failure** — sequential `vmrun suspend` of every source-cluster broker (3 of them), 2 s gap between to dodge the `0.H.6` VMware-under-load concurrency flake.
3. **Verify target keeps serving** — single SSH command on a target broker: create a fresh RF=3 probe topic, produce a unique token, consume it back. Retry on a 3 s poll interval, 90 s deadline. **RTO = T_targetHealthy − T_failureInjected.**
4. **Auto-recovery** — sequential `vmrun start nogui` of each suspended broker.
5. **Wait for source healthy again** — best-effort `kafka-metadata-quorum.sh` poll on a source broker, 4 min deadline (cold VM boot + KRaft quorum re-form).

Output: human (Spectre table with timeline + colored result) or `--json` (`KafkaFailoverJsonOutput`).

## What got fixed during the run

- **`SshKeyDiscovery` preferred the user's personal `~/.ssh/id_ed25519` over the lab-canonical `~/.ssh/nexus_gateway_ed25519`.** The system `ssh.exe` resolves the right key via `~/.ssh/config`'s `Host 192.168.70.*` stanza (→ `IdentityFile ~/.ssh/nexus_gateway_ed25519`); SSH.NET, used by the CLI, does not parse `ssh_config` and was falling back on the first `id_ed25519` it found — which is the operator's personal/GitHub key and is NOT authorized on any lab VM. Surface symptom: every SSH-using verb's pre-flight failed with `Permission denied (publickey)` against the kafka tier. Fix: `SshKeyDiscovery.DefaultRelativePaths` now prefers `nexus_gateway_ed25519` first, then `id_ed25519`, then `id_rsa`. The unavailable-message names the lab-canonical path explicitly.

  This silently affected every SSH-using verb (`failover-test consul-leader`, `failover-test nomad-leader`, `failover-test swarm-manager`) on any build host where the operator has a personal `id_ed25519` distinct from the lab key — likely most build hosts. The kafka failover surfaced it first because the kafka tier was the next-built fleet to exercise the CLI's SSH path.

## What got fixed during the run

Two iterations to get from "code shipped, AOT builds, unit tests pass" to "both directions green on the live tier":

1. **`SshKeyDiscovery` preferred `~/.ssh/id_ed25519` over `~/.ssh/nexus_gateway_ed25519`.** The system `ssh.exe` resolves the right key via `~/.ssh/config`'s `Host 192.168.70.*` stanza (→ `IdentityFile ~/.ssh/nexus_gateway_ed25519`); SSH.NET, used by the CLI, does not parse `ssh_config` and was falling back on the first `id_ed25519` it found — which is the operator's personal/GitHub key and is NOT authorized on any lab VM. **Surface symptom:** every SSH-using verb's pre-flight failed with `Permission denied (publickey)`. **Fix:** `SshKeyDiscovery.DefaultRelativePaths` now prefers `nexus_gateway_ed25519` first, then `id_ed25519`, then `id_rsa`. The unavailable-message names the lab-canonical path explicitly.

   This silently affected every SSH-using verb (`failover-test consul-leader`, `failover-test nomad-leader`, `failover-test swarm-manager`) on any build host where the operator has a personal `id_ed25519` distinct from the lab key — likely most build hosts. The kafka failover surfaced it first because the kafka tier was the next-built fleet to exercise the CLI's SSH path.

2. **Pre-flight health probe matched the wrong field name.** `kafka-metadata-quorum.sh ... describe --status` on Apache Kafka 3.8 outputs `LeaderId:` + `LeaderEpoch:` + `CurrentVoters:`; my initial code grepped for `CurrentLeader:` (the older KRaft-draft field name). **Surface symptom:** "pre-flight: target cluster is not healthy -- refusing to inject failure" against a perfectly healthy cluster. **Fix:** the probe now regex-matches `LeaderId:\s+(\d+)` and verifies the parsed integer is positive — the canonical signal that a quorum has elected a voter as leader.

Both are landed in v0.5.0 and recorded here so future contributors don't repeat them.

```json
  "targetServedAfterFailure": true,
  "targetProbeToken": "probe-018a917d9c7a43ce",
  "rtoSeconds": 13.2,
  "recovery": "recovered",
  "recoveryHint": null,
  "timeline": {
    "preFlightCompletedSec": 3.08,
    "failureInjectedSec": 15.26,

    "recoveryAttemptedSec": 43.55,

```

Source-gen `JsonSerializerContext` — AOT-safe, no reflection at runtime.

```
$ nexus kafka --help
DESCRIPTION:
    Kafka DR helpers (Phase 0.H Kafka ecosystem must be live).

COMMANDS:
    failover    Drive a region-loss DR failover between the East + West
                KRaft clusters and measure RTO. See ADR-0008 for the
                v0.5.0 demo-grade scope.

$ nexus kafka failover --help
COMMANDS:
    east-to-west    Vmrun-suspend the 3 kafka-east brokers (HOST-LEVEL
                    region-loss simulation); verify kafka-west keeps
                    serving via an RF=3 produce/consume round-trip;
                    measure RTO; vmrun-resume to recover.
    west-to-east    Vmrun-suspend the 3 kafka-west brokers (HOST-LEVEL
                    region-loss simulation); verify kafka-east keeps
                    serving via an RF=3 produce/consume round-trip;
                    measure RTO; vmrun-resume to recover.
```

Exit-code semantics:

| Code | Meaning |
|---|---|
| 0 | Failover succeeded — target served the produce/consume round-trip AND source was recovered cleanly. |
| 1 | Target did NOT serve under source-loss — DR posture is broken. |
| 2 | Service-side error (pre-flight failed, vmrun suspend failed, recovery failed). |
| 3 | Operator aborted at the interactive confirmation prompt. |

## What's deferred to v0.5.1+

- **Real per-consumer-group offset translation** via MM2's `<src>.checkpoints.internal` topic (option B in [ADR-0008](../adr/ADR-0008-kafka-failover-demo-grade-via-ssh.md)). Building this now would ship under-exercised — no real consumer app exists in the lab yet to translate offsets FOR. The first real consumer is `streamcore` (Phase 12); building B alongside that lets us test against actual consumer behaviour.
- **A `--reverse` reconcile mode** for "east came back up, replay west's drift back into east" (per DEMO-08 §4). Same reason — needs a real consumer to be meaningful.
