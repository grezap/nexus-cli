## Live-caught issues (the lessons)

The adapter CODE was first-try-green on every verb. The genuine live-caught issue was **infra**:

1. **`failover` → `403, client certificate required`** (the 0.G.4 PatroniAdapter bug #1). REST
   `verify_client: optional` requires a client cert for state-changing POSTs; patroni.yml had no `ctl:`
   block so `patronictl` presented none. **Fixed live** — appended a `ctl:` block (cacert/certfile/keyfile
   = the node's own TLS) to all 6 PG nodes (no restart; ctl is client-only) — and **baked** into
   `role-overlay-citus-patroni-bootstrap.tf` (v2). Re-ran failover: green (RTO ≈ 1.6 s).
2. **patroni.yml mode must stay `0640 postgres:postgres`** (the daemon runs as `postgres`). A stray
   `chmod root:root` during the live `ctl:` edit made a restarted member crash-loop (`PermissionError:
   /etc/patroni/patroni.yml`); the running leader, holding the file open, was unaffected — which is why it
   surfaced only on the `scale-out add` rejoin. Restored `0640 postgres:postgres` on all 6 nodes (the
   overlay already `install -m 0640 -o postgres -g postgres`, so cold-rebuild is correct). After the fix,
   `scale-out add` rejoined in 4.5 s.

Design decisions (not bugs): etcd health unions the per-node "is healthy" endpoint names (the 127.0.1.1
self-probe artifact); backup is an operator `COPY` round-trip (pg_dump on a coordinator doesn't dump worker
data); scale-out is Patroni-member-level (worker-group growth = apply-on-demand, ADR-0042).

## Cold-rebuild — PROVEN 2026-06-18

`citus.ps1 destroy` (56 destroyed, clean — state holds the non-x86 vmrun_path) → from-zero `citus.ps1 apply`
(`-parallelism=3`) → **smoke-0.P ALL CHECKS PASSED** (incl the destructive worker-Patroni-failover test) →
**full verb matrix re-ran GREEN** against the rebuilt cluster (status 9 nodes · health green incl etcd-union
3/3 + sharding 16/16 + distributed-query 800 · topology Shards populated · failover worker2 switchover
recovered · backup take 5.5 KiB + restore **800** · cert-rotate 9/9 0-errors 66s · acl grant propagated ·
chaos recovered · scale-out remove+add rejoined streaming). The operator-user overlay, the patroni `ctl:`
block, the security creds-seed (operator-password) + agent policy (operator-password read) all came up
**in-graph** — the operator-user overlay printed `OPVERIFY=800` (distributed query as the operator) on the
fresh cluster.

**1 real source bug surfaced (the rebuild's value — a warm live-verify can't catch it):** the
`role-overlay-citus-patroni-bootstrap.tf` staging dispatched the base64 patroni.yml as an **ssh argv**
(`ssh … "echo '<b64>' | base64 -d | bash"`). The v2 config (the added `ctl:` block) pushed `<b64>` over the
**ssh.exe ~8 KB Windows command-line limit** → the argv was truncated → the `echo '<b64>` single-quote was
left unterminated → `bash: -c: line 1: unexpected EOF while looking for matching '`. **Fixed:** pipe the
base64 via **STDIN** (`$stageB64 | ssh … "tr -d '\r' | base64 -d | bash"`), matching the extension/distribute
overlays' `bash -s` idiom — no argv size limit. ([[feedback_ssh_stage1_size_limit]].)

**1 transient (recovered by re-run):** the pre-existing `citus_extension` overlay failed at
`citus_add_node` with `cannot execute DELETE in a read-only transaction` / `failure on connection marked as
essential: worker1…:5432` — the keepalived VIP for worker1 was briefly on the read-only replica during the
post-`citus_add_node` metadata sync (the T7-family settle race). Re-running apply once (VIPs settled
read-write) completed it cleanly; the overlay is idempotent. Two verb-matrix verbs (`backup take`, `acl
grant`) also returned empty/errored on the FIRST attempt when run **immediately after a failover-test**
(cluster still settling — the distributed COPY fan-out + the CREATE ROLE worker propagation hit the
settling window); both were GREEN on an immediate re-run. Lesson: allow the cluster to settle after a
failover before the next mutating verb.

Adapter source unchanged by the rebuild (the bug was infra/.tf). Lab returned to base after the proof.
