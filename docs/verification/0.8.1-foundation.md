## Live-caught bug (the lesson)

**AD replication probe returned empty metadata.** `Get-ADReplicationPartnerMetadata -Target <dc> -Scope Server
-Server <ip> -PartnerType Inbound` returned an object (`count=1`) whose `LastReplicationResult` /
`ConsecutiveReplicationFailures` fields were all blank, so the health probe stayed yellow ("no inbound partner
metadata yet"). Diagnosed live: the explicit `-Server <ip>` degrades the result; since the Windows-SSH session
already runs ON the target DC (`WinPsAsync(d.Ip, …)`), the **default** `-Server` (localhost) populates the
fields. **Fixed** by dropping `-Server` (and the redundant `-PartnerType`) → both DCs report result=0, failures=0.

The VaultAdapter was first-try-green on every verb — the thorough up-front contract probe (the HTTP control
plane, the drifted-leader read, the `vault.crt`/`vault.key` filenames, the transit-outside-the-bundle handling,
the snapshot-as-gzip-tar inspect) pre-empted the usual 1-4 live bugs.

## Cold-rebuild (Option A — Vault greenfield re-cluster), PROVEN 2026-06-18

Greg consented to the full Vault-only greenfield rebuild (`nexus-infra-vmware` handbook §E.5; AD/forest kept
intact). The platform **trust root** was destroyed and rebuilt from absolute zero, then the v0.8.1 `vault`
adapter re-proven against it.

**Sequence:** pre-flight backup of `~/.nexus/*` sidecars → `security.ps1 destroy` (108 destroyed) →
`security.ps1 apply` (clones vault-transit + vault-1/2/3, fresh `vault operator init`, new PKI root +
intermediate, LDAPS re-issue + NTDS restart, KV re-seed, ~25 downstream AppRole/policy/seed overlays) →
`security.ps1 smoke -Phase 0.D.5` **ALL CHECKS PASSED** (chained 0.D.1→0.D.5, ~80 checks) → the `vault` verb
matrix re-ran GREEN: **status** (vault-1 now active — leaders drift, read dynamically), **health** (7 probes
green incl. raft 3 voters/1 leader + transit-unseal + operator-auth with the **rotated** root token),
**topology**, **failover** (step-down vault-1→vault-2, RTO ≈ 2.2 s), **backup** (raft snapshot 404 KiB,
non-destructive inspect index=1146 term=4), **recover-ha** (all unsealed). The build host's root token was
**overwritten cleanly** (`hvs.eB…` → `hvs.dg…`) by the fresh init — no lockout — and the CLI auto-picked-up
the new token (the `VaultAdminClient` reads `VAULT_TOKEN`/the bundle from the env each run).

**2 real source bugs surfaced + fixed** (a warm live-verify never reaches the clone / CA-rotation paths — the
whole value of a cold-rebuild; foundation/security was the first tier cold-rebuilt since VMware's vmrun
relocation):

1. **`modules/vm/variables.tf` `vmrun_path` defaulted to the deleted `…/Program Files (x86)/…/vmrun.exe`** →
   the clone provisioner failed `vmrun reported … exit 1` on the very first clone. Fixed → the non-x64 path.
2. **`role-overlay-vault-ldaps-cert.tf` idempotency probe was CN-based** (`ldaps_overlay_v` 5→6) — it matched
   dc-nexus's existing cert by *Common Name* + checked that *some* chain builds, so on a Vault greenfield
   rebuild (new CA, SAME CNs, fresh key) it saw the old (still-valid) cert as good and **skipped re-issue**,
   leaving dc-nexus serving an old-CA leaf the rebuilt Vault couldn't verify (`tls: failed to verify … x509:
   certificate signed by unknown authority "NexusPlatform Root CA"`). Fixed → the probe now compares the
   chain's **root thumbprint** to the current Vault root (build-host bundle) and forces re-issue across a CA
   rotation.

**3 transients (recovered, the documented cold-rebuild gauntlet):** (a) post-destroy **zombie VMs** (the
stale-x86 stop left them running; a graceful in-guest `poweroff` re-materialized the `.vmx`) → in-guest
`poweroff` + dir cleanup; (b) **LDAPS NTDS-restart settle window** — `ldap-rotate-role` + the smoke's
`auth/ldap` login each failed on the first attempt right after an NTDS restart and passed once settled (the
overlay's own handshake-verify has an 8-retry loop; the smoke does not); (c) the smoke's `svc-vault-smoke`
policy check failed because the account was **missing from `nexus-vault-readers`** — a side effect of this
session's earlier `acl foundation-ad grant/revoke` verification (restored via `Add-ADGroupMember`, what the
foundation `role-overlay-dc-vault-smoke-account.tf` overlay manages).

**1 latent trap identified + documented (NOT triggered):** the `vmrun_path` default change makes the
**foundation env's existing `clone_vm` state** (dc-nexus / dc-nexus-2 / jumpbox, which hold the old x86 path)
plan as **"must be replaced"** — a `foundation.ps1 apply` would run the destroy-provisioner and delete the
**live DCs'** `.vmx`. Caught by a `terraform plan` pre-check; the foundation apply (canon step 7) was
**deliberately NOT run** (Option A doesn't need it — the only foundation-side need, the group membership, was
restored directly). **RESOLVED** (state-only, the running DCs untouched): the foundation local state's 6
`vmrun` trigger occurrences were literal-replaced x86 → non-x64 and `terraform plan` now reads `No changes`,
so a future `foundation.ps1 apply` is safe. Method documented in `nexus-infra-vmware` handbook §E. Memory:
`feedback_stale_vmrun_path_in_clone_vm_state`.

After the proof, jumpbox was graceful-stopped → base = 6. **No managed-driver / no shelled `vault` binary
changes** — the source fixes are infra `.tf` only; the `nexus-cli` adapter code was unchanged by the rebuild.

## Security posture

The Vault control plane is **HTTP from the build host** using the operator `VAULT_TOKEN` (ADR-0004) — the root
token NEVER reaches a node's process table. Only node-local actions (service control, cert push, chaos,
recover-ha restarts, the transit unseal) use SSH. `recover-ha` is the ONLY exposed unseal path (raw `vault
operator unseal` is never surfaced), and `backup restore` on the live trust root is deliberately refused.
