## Tier state at verify time (the headline finding)

The tier was found in a **post-v0.8.1-Vault-greenfield broken-trust state** (it was OFFLINE during that 2026-06-18/19 rebuild — the same casualty class as the swarm tier's Portainer drift). Three infra divergences, all surfaced by the diagnose-first probe and reported honestly by the adapter (none is an adapter bug):

1. **vault-agent broken trust (tier-wide).** The obs node leaves were issued **2026-05-26 by the OLD "NexusPlatform Root CA"**; the build host's current `vault-ca-bundle.crt` root is the **NEW** root (notBefore 2026-06-19, same CN/different key). The on-node `nexus-vault-agent`s can't re-authenticate (their `ca-bundle.crt` trusts the old root) → no token at `/var/run/nexus-vault-agent/token`, and the build-host CA bundle cannot validate the obs leaves. **This drove the access posture: SSH-local-curl with each node's own `ca.crt`** (always self-consistent) instead of build-host HTTP.
2. **Grafana admin password drift.** The greenfield rotated KV `nexus/observability/grafana/admin-password`; the live Grafana (admin in the shared PG) still holds the pre-greenfield value → admin API 401.
3. **grafana-pg replication split.** grafana-pg-2 was promoted during the 0.I.4 `-Strict` failover test (2026-05-27) and never re-seeded (no `standby.signal`) → both nodes run as primary; Grafana uses pg-1 via VIP .185.

**The clean repair is a Greg-authorized tier trust re-apply** (`observability.ps1`: re-bootstrap the vault-agents vs the new root → re-issue certs → reconcile the Grafana admin password → re-seed the pg standby via `smoke-0.I.4.ps1 -Strict`), mirroring the swarm tier's post-greenfield cold-rebuild. An autonomous grafana-pg standby re-seed was (correctly) policy-denied this session — "diagnose + build the adapter, not repair the cluster."
