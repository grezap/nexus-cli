## Cold-rebuild (CA rollover to the new Vault root) — folded into this build
The registry tier was found **operationally broken** (not just old-root): Harbor app down (only
`harbor-log` up), PG replication dead (both nodes primary), vault-agents old-root/unusable. A
from-zero rebuild to the new Vault root was required to get a healthy tier to live-verify against
(Greg consented). Sequence:

1. **vmrun_path x86 → non-x86** fixed in `nexus-infra-registry` (env `variables.tf` + `modules/vm/variables.tf` + README) — the stale-path trap (the env state held the x86 path in clone_vm).
2. Powered MinIO (4 nodes, lakehouse tier) up first — Harbor's `s3://harbor` blob backend.
3. Graceful in-guest power-off of the 4 registry VMs (dirs unlock for destroy).
4. `registry-harbor.ps1 destroy` (24 destroyed; the stale-x86 destroy-provisioner errors non-terminating, then Remove-Item cleans the unlocked dirs — the kafka/foundation pattern).
5. `registry-harbor.ps1 apply` (`TF_CLI_ARGS_apply=-parallelism=3`) — clones bake the corrected vmrun path; vault-agents re-bootstrap to new-root from the Jun-19 sidecars; certs new-root; PG repl + Redis + VIP + Harbor stack + Vault OIDC; the bootstrap exit gate (push + Trivy scan + cosign + S3 blob) PASSED.
6. `smoke-0.L.4.ps1` — **ALL CHECKS PASSED**.

**Cross-tier transient (CA-rollover class) — the MinIO root drift.** The first apply failed at the
harbor-config MinIO bucket step: `mc: signature does not match`. The v0.8.1 greenfield rotated KV
`nexus/lakehouse/minio/root-password` (to an orphaned value), but the running MinIO kept its
build-time root — so `mc alias set` from KV failed. Reconciled **KV → the running MinIO's actual
root** (a new KV-v2 version; old retained for rollback; Greg-consented; data-preserving — no MinIO
restart, no EC touch). Also pre-reconciled the MinIO `nexus-lakehouse-app` IAM key to current KV
(Harbor's S3 credential), the lakehouse/starrocks-sd precedent. Re-ran the apply → complete. (The
v0.8.3 obs rebuild noted this root drift but could ignore it; Harbor surfaces it because the bucket
step needs the root creds.)

## 1 live-caught adapter bug (fixed in source)
**`harbor-systeminfo` health probe gated on `harbor_version`** → yellow. The UNAUTHENTICATED
`/api/v2.0/systeminfo` returns `auth_mode` but omits `harbor_version` (version is only in the
admin-authed response). Re-gated the probe on `auth_mode` (the meaningful unauthenticated SSO
signal), surfacing version only when present → green. (Re-verified live: overall=green.)

## Two verbs intentionally NOT live-run (honest, precedented — not bugs)
- **`failover --direction registry-db`** — the keepalived `demote.sh` re-attaches **Redis** but
  **not PostgreSQL**, so a VRRP cutover promotes the peer's PG while leaving the demoted node a
  second PG primary (split-brain by design; a real registry-db failover is a DR runbook: promote +
  fence + `pg_basebackup` re-seed). The adapter's VRRP+promote+Redis code path was verified against
  the live keepalived scripts; live execution was deferred to avoid degrading the freshly-rebuilt
  datastore. Mirrors the lakehouse iceberg-pg + obs grafana-db precedent. The app tier needs no
  failover (RR DNS; clients retry) — the verb refuses an app-direction with that pointer.
- **`acl grant/revoke` on a real user** — Harbor in `oidc_auth` mode returns **403 on local-user
  creation** (users onboard via OIDC login), so a throwaway target user can't be created from the
  CLI/API; a real OIDC-onboarded user needs the AD→Vault-OIDC browser flow. The grant/revoke API
  path (`PUT /users/{id}/sysadmin`), the user-resolution, and the protected-admin guard are all
  verified; toggling a real onboarded user is the only un-run leg. Mirrors the obs acl partial-proof.
