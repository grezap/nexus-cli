## What shipped

`PatroniAdapter` (`src/Nexus.Cli.Adapters/Cluster/PatroniAdapter.cs`) implements all of
`IClusterAdapter` via SSH-shell-out to on-node `patronictl` / `psql` / `pg_dump` / `etcdctl` (no
managed Npgsql driver — NetArchTest-enforced). It authenticates as the dedicated
`nexus-cluster-admin` role (LOGIN CREATEROLE CREATEDB REPLICATION + pg_monitor/pg_read_all_data/
pg_write_all_data, **not** superuser); that password comes from **Vault KV**
(`nexus/oltp/patroni/operator-password`) via `INexusVaultClient` (ADR-0011 model, unchanged
framework). Registered in `ClusterBootstrapper`. AOT win-x64 **24.18 MB / 30 MB** (+0.15 MB over
percona); **71/71** tests.

## Three control planes (ADR-0013)

- **Patroni** — `patronictl list` (leader/replica + lag) for status/topology; `patronictl
  switchover` for failover. REST `:8008` (`verify_client: optional` ⇒ client cert required for
  state-changing calls — see bug #1).
- **etcd** — RBAC-enabled DCS; `nexus-etcdctl --user root:<pw> endpoint health` for quorum (password
  read on-node via the etcd node's own Vault Agent token).
- **HAProxy** — VIP `.60:5432` routes via `option httpchk GET /leader` to the **current leader
  only**; the stable operator write endpoint (failover RTO is measured here).

## Bugs caught + fixed by live-verify (the headline lesson — 4, same cadence as mongo/percona)

1. **patronictl switchover 403 "client certificate required."** Patroni REST `verify_client:
   optional` **requires** a client cert for POST `/switchover`; patroni.yml had no `ctl:` section so
   patronictl presented none. Fix: a `ctl:` block (`cacert`/`certfile`/`keyfile` = the node's own
   TLS — the CA-signed server cert doubles as a client cert), live-appended to the 3 PG nodes (no
   restart — `ctl:` is client-only) **and** baked into `role-overlay-patroni-bootstrap.tf`
   (`patroni_bootstrap_v` → "2") so cold rebuilds inherit it. Without this fix *no* operator could
   switch over this cluster.
2. **patronictl exits 0 even on a REFUSED switchover.** Validate the `"Successfully switched over"`
   banner in stdout, not the exit code.
3. **`backup restore` permission denied / "must be owner of table."** The operator's
   `pg_read/write_all_data` are DATA grants, not DDL — it cannot `CREATE SCHEMA` in db `postgres`.
   Fix: restore into a fresh **database** the operator OWNS (it has CREATEDB), and `pg_dump
   --no-owner --no-privileges` (else the dump's `ALTER … OWNER TO nexusops` fails).
4. **`cert-rotate` vault issue 500.** Used domain `etcd.nexus.lab` for etcd nodes — the PKI role
   `patroni-server` only allows `patroni.nexus.lab` (the original etcd/haproxy certs are
   `<node>.patroni.nexus.lab`). Fix: all 8 nodes use `patroni.nexus.lab`.

triggers — a plain `apply` would plan to replace clone_vm and **delete the .vmx** (see

the new `role-overlay-patroni-operator-user.tf` + the `ctl:` block in the apply graph.

**5th bug — surfaced by the cold-rebuild (latent infra, orthogonal to the adapter):** the HAProxy
unit runs `User=haproxy` (unprivileged) while `haproxy.cfg` had `chroot /var/lib/haproxy` — chroot(2)
needs root/CAP_SYS_CHROOT, so the fresh nodes failed every start with "Cannot chroot(/var/lib/haproxy)"
(StartLimitBurst hit; no pg_pool backend ever UP). The two privilege-drop mechanisms (haproxy-native
`user/group/chroot` vs systemd `User=`) are mutually exclusive; the running cluster only ever started
haproxy once (pre-this-rebuild) so the conflict stayed latent. Fix: drop the `chroot` directive from
the rendered `haproxy.cfg` (`role-overlay-haproxy-config.tf` v3) — `User=haproxy` already provides the
privilege drop, and the unit's `RuntimeDirectory=nexus-haproxy` provides the tmpfs `/run/nexus-haproxy`.
