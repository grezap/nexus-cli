## What shipped

`ClickHouseAdapter` (`src/Nexus.Cli.Adapters/Cluster/ClickHouseAdapter.cs`) implements all of
`IClusterAdapter` via SSH-shell-out to on-node `clickhouse-client` (native TLS `:9440`) + the Keeper
four-letter-word interface (`echo mntr | nc 127.0.0.1 9181`) — **no managed `ClickHouse.Client`
driver** (NetArchTest-enforced). It authenticates as the dedicated `nexus-cluster-admin` ClickHouse
user (`sha256_password`, `GRANT ALL ON *.* WITH GRANT OPTION`, distinct from the engine's built-in
`admin`); that password comes from **Vault KV** (`nexus/analytics/clickhouse/operator-password`) via
`INexusVaultClient` (ADR-0011 model, unchanged framework). Registered in `ClusterBootstrapper`. AOT
win-x64 **24.84 MB / 30 MB** (+0.66 MB over patroni); **71/71** tests.

## Auth-model decision (from a live probe, not assumption)

ClickHouse is **password-auth**, not mTLS-only like Redis. The wire is mTLS (`:9440`,
`verificationMode relaxed`) but SQL users authenticate by `sha256_password`, and the `default` user
is loopback-only (127.0.0.1/::1) — so every networked client must present a password. → reuse the
LOCKED Vault-KV operator-credential model: a dedicated `nexus-cluster-admin` operator whose password
lives only in Vault KV. The existing `admin`/`app` users (also sha256, also Vault-KV-seeded) stay as
the engine's built-in accounts.

## Two control planes (ADR-0014)

- **SQL / data plane** — `clickhouse-client --secure --accept-invalid-certificate --port 9440` for
  `system.clusters`/`system.replicas`/DDL/RBAC/BACKUP; the Distributed table `nexus.events` over
  `ReplicatedMergeTree` `nexus.events_local`, `internal_replication=true`, 3 shards × 2 replicas.
- **Coordination plane (Keeper)** — `echo mntr | nc 127.0.0.1 9181` → `zk_server_state`
  (leader/follower); the 3-node C++ RAFT quorum (NOT ZooKeeper, ADR-0028). The cluster's only
  cluster-wide leader (the data plane is leaderless / every replica writable).

## Bug caught + fixed by live-verify

1. **`access_management` is NOT a per-user `SETTINGS` value** (CH 26.5 → `Code 115 … neither a
   builtin setting nor … 'SQL_' …`, caught while creating the operator). For a **SQL-created** user
   the access-management capability comes from the **`GRANT ALL` privilege group**, not the XML-only
   `access_management` setting. Fix: create the operator with no SETTINGS clause + `GRANT ALL ON *.*
   WITH GRANT OPTION` — verified to confer `CREATE USER`/`CREATE ROLE ON CLUSTER`. (The thorough
   up-front study of the schema-bootstrap / TLS / backup overlays kept the remaining verbs
   first-try-green — the established Redis/Mongo/Percona/Patroni shapes carried over cleanly.)

## Infra (mirrors the percona/mongo/patroni operator-user model)

- **nexus-infra-vmware/envs/security** — `role-overlay-vault-clickhouse-creds-seed.tf` **v2**
  (+`operator-password`, sticky-seeded; admin/app left untouched). Applied live (targeted apply of
  the single `vault_clickhouse_creds_seed` resource; the security env has no VMs → safe — verified a
  ClickHouse node's own agent token reads the 32-char operator-password). **No agent-policy change**
  was needed: the existing `nexus-agent-clickhouse-*` policy already wildcard-reads
  `nexus/data/analytics/clickhouse/*`.
- **nexus-infra-analytics/envs/analytics-clickhouse** — new `role-overlay-clickhouse-operator-user.tf`
  (read operator-password on the DDL coordinator via the agent token → distributed-DDL readiness gate
  → idempotent `CREATE USER … ON CLUSTER` + `GRANT ALL WITH GRANT OPTION` → verify the operator auths
  + manages access) + var `enable_clickhouse_operator_user`. The operator user was created on the
  running cluster via the overlay's exact, idempotent SQL over SSH (non-destructive) so adapter
  live-verification could proceed; it is `ON CLUSTER` (present on all 6 data nodes) and authenticates
  over the native-TLS wire.

## Cold-rebuild proof — ⏳ PENDING operator consent

The `analytics-clickhouse` terraform state carries the **stale x86 `vmrun_path`** (variables.tf line
22 default = `C:/Program Files (x86)/…/vmrun.exe`) in its clone_vm/power_on triggers — a plain
`apply` would plan to replace clone_vm and **delete the .vmx** (see
`feedback_stale_vmrun_path_in_clone_vm_state`). The clean path is a from-zero **cold-rebuild**
(destroy → packer-built keeper+server templates → apply → `smoke-0.G.5.ps1`), which (a) bakes the
correct non-x86 vmrun_path into fresh state, and (b) proves the new
`role-overlay-clickhouse-operator-user.tf` + the creds-seed v2 operator-password in the apply graph.
This is a destroy of shared infra → **gated on explicit operator consent**. When run, this section
flips to **✅ PROVEN** with: fresh-cluster evidence (the operator-user overlay ran in-graph,
`smoke-0.G.5.ps1` ALL GREEN, the verb matrix re-run GREEN against the rebuilt cluster) + any
cold-rebuild-surfaced transients chronicled.
