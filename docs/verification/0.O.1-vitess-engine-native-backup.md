# 0.O.1 — Vitess engine-native BackupStorage (live verification)

**Date:** 2026-07-09 · **Tier:** vitess (12 VMs) · **Repos:** `nexus-infra-vitess` (infra overlay + templates + smoke) + `nexus-cli` (`VitessAdapter` backup/restore)

Closes the third pre-Phase-1 infra-hardening item: **0.O.1 Vitess BackupStorage** — gives the vitess
tier a real Vitess `file` BackupStorage backend on shared NFSv4 driven by the `xtrabackup` engine, and
rewrites `VitessAdapter` backup/restore from the pre-0.O.1 logical `mysqldump` to engine-native
`vtctldclient BackupShard` / `RestoreFromBackup`. Done as a **targeted overlay apply — no cold-rebuild**
(the operative guidance: evaluate the cheapest path first, like iceberg-pg / registry-db).

## The gap (diagnosed live before the change)

```
GetBackups commerce/-80  →  "no registered implementation of BackupStorage"
```

No BackupStorage backend, no xtrabackup installed. The v0.7.2 CLI backup verb was a sharding-aware
logical `mysqldump` per shard into a node-local `.sql.gz` (restore = reload into a throwaway verify DB
+ count). Engine-native `BackupShard`/`RestoreFromBackup` were deferred to 0.O.1.

## The fix

### Infra — `role-overlay-vitess-backup-storage.tf` (var `enable_vitess_backup_storage`, runs after schema)

- **NFS `file` repo, self-contained in the tier.** NFS **server** co-located on the control node (.193)
  exports `/srv/nexus-vitess-backups` over NFSv4 (`fsid=0` pseudo-root) to the VMnet10 backplane
  (`192.168.10.0/24` — the nftables backplane rule already accepts it; :2049 needs no new opening) and
  bind-mounts it at `/vt-backups` so vtctld reads the repo locally. All **6 tablets** mount
  `192.168.10.193:/` at `/vt-backups` and install `percona-xtrabackup-84`. vitess uid/gid is identical
  fleet-wide (999/989) → NFS numeric id-mapping just works.
- **vttablet/vtctld flags:** `--backup-storage-implementation file --file-backup-storage-root
  /vt-backups` (both), plus `--backup-engine-implementation xtrabackup --xtrabackup-root-path /usr/bin
  --xtrabackup-user vt_dba --xtrabackup-stream-mode xbstream` on tablets — appended to the single-line
  `VTTABLET_FLAGS`/`VTCTLD_FLAGS` env values (idempotent, sudo-grep-guarded), then a **non-disruptive
  rolling `vttablet` restart** (replicas first, primaries last; mysqld stays up under mysqlctld → no
  reparent). vtctld restarts once.

### The three non-obvious Vitess/xtrabackup gotchas (all found live, all baked into the overlay)

1. **`--mycnf-file` per tablet** (`/var/lib/nexus-vitess/vt_<uidpad>/my.cnf`). The backup engine needs
   mysqld's my.cnf, but here mysqld is owned by **mysqlctld** (not launched by vttablet), so vttablet has
   none → `TabletManager.Backup ... cannot perform backup without my.cnf`.
2. **DROP `--db-socket`.** Even with `--mycnf-file` set, vttablet logged
   `initConfig: connection parameters were specified. Not loading my.cnf.` → `mysqld is unmanaged or
   remote` → `Cnf==nil`. With any db connection param present vttablet treats mysqld as external and
   skips the my.cnf. Removing `--db-socket` puts it in **managed** mode: it reads the socket from the
   my.cnf and still authenticates via the per-user `--db-*-user/password` flags (tablet stays a healthy
   serving replica).
3. **`[xtrabackup]` creds in the my.cnf.** Vitess runs xtrabackup with `--defaults-file=<the mysqld
   my.cnf>` **and a clean environment**, and never passes a password — so `MYSQL_PWD`, `HOME`/`~/.my.cnf`
   and `/etc/my.cnf` are all ignored, and xtrabackup connected `using password: NO` → `Access denied for
   'vt_dba'@'localhost'`. The creds must live in the my.cnf's `[xtrabackup]` group. Put them in
   **`ssl.cnf`** — which is **already in the RUNNING mysqlctld's `EXTRA_MY_CNF`** — so every my.cnf
   regeneration (mysqld restart / RestoreFromBackup / reboot / cold rebuild) re-merges them with **no
   disruptive mysqlctld restart**. (A fresh entry added to `mysqlctld.env` would NOT reach the live
   mysqlctld process, whose env is fixed at service start — proven when a RestoreFromBackup regenerated
   the my.cnf without the creds.) Also appended to the live my.cnf directly for immediate effect.

### Software — `VitessAdapter`

- `BackupTakeAsync` → `vtctldclient BackupShard commerce/<shard>` per shard (auto-selects a REPLICA;
  primary untouched), reads the new backup name/size from `GetBackups`.
- `BackupRestoreAsync` → `RestoreFromBackup --dry-run` per shard by default (non-destructive validation);
  with `--confirm-destructive`, a real `RestoreFromBackup` onto a REPLICA per shard + wait-for-rejoin +
  restored-row count. `--at <YYYY-mm-DD.HHMMSS>` selects a specific backup.

### Templates + smoke (cold-rebuild reproducibility)

- Tablet template bakes `pxb-84-lts` repo + `percona-xtrabackup-84` + `nfs-common`; gate template bakes
  `nfs-kernel-server` (overlay still installs idempotently as fallback).
- `smoke-0.O.ps1` §9.5 (6 checks): backend registered, xtrabackup+xbstream present, `/vt-backups`
  NFS-mounted+writable, control bind-mount, **end-to-end `BackupShard -80` lands in `GetBackups`**.
